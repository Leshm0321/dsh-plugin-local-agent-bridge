# 安全

## 信任边界

公司主机是可信的。它拥有已安装的 Claude Code 和 Codex 产品、它们既有的登录状态、选中的工作区、本地工具、MCP 访问权限和子进程。远程浏览器和访问网络的可信度较低。

客户端只会收到：

- 不透明的桥接会话 ID、轮次 ID 和交互 ID。
- 产品名、产品版本、兼容性，以及安全的健康状态。
- 脱敏后的文本、思考、工具、文件变更、状态和错误事件。
- 一次性的审批与提问表单。

客户端**绝不**应收到产品的账号身份、套餐详情、原生会话定位符、凭据路径、cookie、OAuth 令牌、API key、登录 URL 或设备码。

## 远程访问的必要约定

让 DeepSeek Harness 保持绑定在 `127.0.0.1`，并在它前面放一层：

- 私有覆盖网络，例如 Tailscale、Headscale 或 WireGuard。
- 带认证的反向代理，使用 OIDC、Passkey、mTLS 或公司 SSO。

这个访问层必须提供 TLS、用户或设备认证、WebSocket 转发、正确的 Host 与 Origin 处理、空闲会话过期，以及访问日志。DSH 的 `trustedHosts` 配置只能作为额外的一道防主机重绑定围栏，绝不能当作唯一的认证手段。

不要用未认证的 FRP 隧道、路由器直接端口转发、绑定到公网 `0.0.0.0`，或者「一个别人猜不到的 URL」来充当访问控制。

## 认证隔离

插件只启动从 `PATH` 解析出的主机可执行文件：

- `codex app-server --stdio`
- 经官方 Agent SDK 调用的主机 `claude` 路径

插件不实现账号登录、不调用 `account/login/*`、拒绝 URL 模式的 MCP 征询，也不读 `.claude`、`.codex`、`auth.json` 或操作系统的凭据存储。产品的认证过期时，浏览器收到的是 `HOST_AUTH_REQUIRED`；重新认证在主机上手工完成。

## 审批策略

交互使用随机 UUID，并绑定到唯一的桥接会话和轮次。响应是一次性的。迟到的、重复的、会话不符的、类型不符的响应都会被拒。取消或主机重启会把悬着的交互判为已取消或已过期。没有自动批准，也没有持久化的放行规则。

审批摘要包含工具名，以及在产品协议提供时的脱敏目标。浏览器上的一次批准只授权当前这一个请求，并不意味着底层那条命令是可回滚的。

## 脱敏与存储

每一条持久化记录和发往浏览器的事件都过一遍共享的脱敏器。文本被截断，形似机密的对象键被替换，凭据路径、bearer 令牌、API key、OAuth URL 和形似设备码的字符串被移除。作为桥接 ID 的标准不透明 UUID 被保留，这样浏览器的响应才稳定。持久化层会拒绝仍能命中凭据泄漏探针的记录。

原生会话定位符是仅存于主机的持久映射，它们从不出现在 Remote 的 schema 里。子进程的完整环境变量既不记日志也不持久化。

## 安全验证

发布验证必须包含：

- 浏览器请求白名单检查：对 Anthropic、Claude、OpenAI、ChatGPT 或产品 API 域名的请求必须失败。
- 对浏览器存储、cookie、下载、Remote 载荷、stdout、stderr 和界面做凭据「探雷」值扫描。
- 检查客户端里不存在任何登录动作、OAuth URL、设备码或令牌输入。
- 重复响应与迟到响应的交互测试。
- 取消、卸载和主机关停之后的进程树清理证据。

自动化的 fixture 只用合成值。永远不要把真实凭据写进测试报告。

## 枚举产品状态

面板会列出一个产品的斜杠命令、技能、MCP 服务器和可恢复的会话。这些全部来自产品自己的 API——Agent SDK 的 `supportedCommands`、`mcpServerStatus` 和 `listSessions`，以及 Codex 的 `skills/list`、`mcpServerStatus/list` 和 `thread/list`。插件不读 `~/.claude`、`~/.codex`，也不读它们下面的任何文件，所以「不碰产品状态目录」这条禁令并没有因为这些功能而松动。

两个产品在这些回复里都会给出绝对文件系统路径：每个技能一个 `SKILL.md` 路径，每个会话一个转录文件路径。这些字段在**解析回复的地方就被丢掉**，而不是带着往下游走再脱敏，所以主机的文件系统布局不会到达浏览器。任何确实要跨过去的字符串——会话标题、技能描述——都和其他产品文本走同一套脱敏。

原生会话定位符对桥接来说是不透明的。它被交给产品自己的 resume 路径，从不被解析、从不拼进路径、也从不用来打开文件。

## 浏览主机文件系统

输入框的文件按钮可以列出运行 Harness 那台机器上的任意目录，并把绝对路径返回给浏览器。这是面板范围最宽的一次读取，而它默认开启，基于三条成立的理由：

- **平台本身已经这么做了。** `workspaces.listDirectory`——Harness 自己的工作区选择器——就在枚举主机目录并把绝对路径返回给浏览器。本功能只是在那个视图里补上了文件，因为那个选择器只返回目录。它在 `src/core/host-browse.ts` 里自行实现而不是委托出去，原因同上，另外还因为 `listDirectory` 依赖某个 `browse` 能力，而合成出来的 Profile 未必提供它。
- **Agent 本来就能读这些路径。** 两个产品都接受绝对路径并读取它，受会话的权限模式约束。浏览只是省掉操作者去敲一条他本就知道的路径；它没给 Agent 任何原先没有的能力，而 Agent 读工作目录之外的文件时，除非权限模式另有规定，仍然要走审批。
- **它是有界的。** 每次请求一层、500 条、只给绝对路径和类型。它从不返回文件内容、从不递归，而且对相对路径直接拒绝——不会拿主机进程当前所在的目录去解析它。

但它终究是浏览器此前做不到的一次读取。只要部署中浏览器比回环地址更远，就在 Profile 配置里设 `allowHostBrowsing: false`：此时面板会干脆不提供这条入口，而不是给一个必然失败的按钮，主机侧也直接拒绝该调用。

注意它与本文别处那条脱敏规则的区别。出现在**产品回复里**的绝对路径仍然在解析处被丢掉——那是主机把自己的布局泄进了产品文本。而操作者自己一路点进去选中的路径恰恰相反：那是他的选择，也是唯一值得返回的东西。

## 浏览器在工作目录里写的文件

`allowWorkspaceWrites` 打开时（默认如此），侧边栏可以在会话的工作目录内创建、重命名、删除和编辑文件。这是浏览器唯一能写入任意路径的地方，规则都在 `src/core/workspace-files.ts` 里：

| 规则 | 为什么 |
| --- | --- |
| 限定在工作目录内，且在符号链接解析之后才做检查 | 一个被提交进仓库的链接，不能成为往目录树外写文件的通道。读的一侧也有这道检查，但会造成破坏的是写 |
| 创建和重命名限定的是**父目录**，且要求最后一段是单一名称 | 目标还不存在，所以「路径已存在」那套检查用不上；限定父目录才能挡住 `a/../../b` 借一个本身在内的目录伸出去 |
| 父目录必须已经存在 | 一次手误不该凭空造出一棵没人要的目录树 |
| 创建和重命名从不覆盖 | 「新建文件」和「抹掉那个文件」是两种意图，而只有一种被表达了 |
| 删除从不递归，非空目录直接拒绝 | 一个从浏览器就能触达的递归删除，等于让一次误点就能丢掉一个仓库 |
| 工作区根目录本身不能删 | 那绝不会是本意 |
| 写入必须带上读到该文件时的修订号，不一致就拒绝 | Agent 就在同一棵树上干活。一个「缓冲区里是什么就写什么」的面板，会悄悄抹掉 Agent 的成果 |
| 每次写入上限 2 MB | 刻意比读的上限更小：读一个大文件只是看看，写一个大文件是改动，而那么大的缓冲区不可能是谁手打出来的 |

如果部署要服务跨网络的客户端，请设 `allowWorkspaceWrites: false`。此时面板不显示这些控件，主机侧也拒绝这些调用。

## 浏览器发往主机的文件

这个桥接里其他每条路径都是把数据往外带。输入框的上传是往里带，而它存在只为一个理由：当 Harness 跑在另一台机器上时，操作者自己笔记本上的文件没有别的办法到达 Agent。引用工作目录里已有的文件仍然是默认做法，而且它不复制任何东西。

正因为它反了方向，规则收得很紧，而且全部在主机侧强制，位于 `src/core/uploads.ts`：

| 规则 | 为什么 |
| --- | --- |
| 唯一目的地：会话工作目录下的 `.dsh-bridge-uploads/`，从主机自己的工作区注册表解析得出 | 浏览器从不指定目的地，所以根本没有一个供它影响的路径参数 |
| 每一段路径都按白名单重建：字母、数字、`.`、`_`、`@`、空格和 `-` | 黑名单得穷举分隔符、穿越写法、控制字符和 Windows 保留标点，而且总可能漏掉一个 |
| 只由点组成的段被拒；除此之外开头的点保留 | `..` 是穿越，而 `.env.example` 是有人真想发过来的文件 |
| 路径拼好之后，再对该目录的真实位置重新断言一次包含关系 | 既能抓住重建过程本身的失误，也能像 `@` 那样正确处理经符号链接到达的工作目录 |
| 以 `wx` 写入，绝不替换；碰撞时加数字后缀 | 上传永远不可能销毁操作者的成果，而且「什么已经存在」由文件系统决定，不是由一次事前检查决定 |
| 单文件 8 MB、单请求 32 MB、50 个文件、深度 8、每段 96 字符 | 浏览器不能靠一次次请求把主机磁盘塞满 |
| base64 严格解码，靠往返比对 | Node 的解码器会忽略它不认识的字符，否则一个畸形载荷会被按它「解析成了什么」写进去 |

被拒的文件会被计数并上报，所以面板会说「有些没送到」，而不是默默少交几个。

上传的字节是操作者自己的文件，是他有意发过来的。它们不做脱敏：脱敏的存在是为了不让产品凭据到达浏览器，而改写一个别人特意让 Agent 去读的文件的内容，只会把它弄坏。把上传目录当作操作者提供的内容看待，并注意 Agent 读它时，与任何其他工具调用受同一个权限模式约束。

上传功能在 `tests/unit/uploads.spec.ts` 里针对真实目录做过验证，覆盖两种路径分隔符的穿越写法、POSIX 与 Windows 的绝对路径、经符号链接到达的工作目录、碰撞处理，以及畸形 base64。
